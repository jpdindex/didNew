경기장 구역 체계

03.areacode.sql 이 유일한 근거다. APK 디컴파일로도 같은 개념을 확인했다.

  • 원본 캔버스 971 × 634, 가로 6칸 × 세로 3칸 = 18구역
  • 열 경계 [0, 152, 318, 484, 651, 818, 971]
  • 행 경계 [0, 180, 451, 634]
  • 진영 선택값 + 전/후반으로 방향(L/R)이 정해지고, 방향에 따라 번호가 반전된다 — zone = dir === 'L' ? 19 - zoneR : zoneR

경기장을 클릭하면 해당 구역이 잠깐 밝아졌다 사라진다(420ms).

DAP 판정

  • DTP / STP — 루트 안의 모든 레코드가 DAP 로 인정된다.
  • UTP — 공격영역 진입 시점 이후는 전부 인정, 진입 이전은 2개까지만 인정.
  • act 가 비어 있는 레코드는 항상 제외 (isDap = !!act).

선수 역할

DTP/STP 루트를 역순으로 훑으며 부여한다. DTS(슈터) → DTA(어시스터) → DTM(메이커) → 그 이전 전원 DTB(빌더). 골로 이어진 경우 AST GTM GTB 가 함께 붙는다.

BAP

DAP 와 무관한 별도 카운터. Ready / Keep 상태머신으로 판정하며 4초 공백, 결과 발생, 공격영역 진입, 중앙선 돌파 등이 트리거다.

채택한 기준

우리가 다시 만드는 것은 입력 단말(DID) 자체이고, 실제 운영에서 관측된 동작도 "X/B/슛이 나오면 연결이 끊긴다" 이므로 단말 로직을 기준으로 삼았다.

데이터 모델

플레이 하나 = 레코드 하나

APK 디컴파일로 확인한 실제 동작이다.

단계동작결과
액트 버튼
(C/P/K/F/S/H/R)		setActCode(act) + setResCode("O")act='C', res='O'
결과 버튼
(X/B, 골대 존)		같은 레코드의 res 만 덮어씀act='C', res='X'
예외
슛에 X/B		위 + setActCode(null)act='', res='X'
  • 'O' 는 계산용 임시값이 아니라 앱이 실제로 저장하는 값이다 (DPlayInputDefaultFragment.java:151).
  • 결과를 별도 레코드로 나눠 저장하지 않는다.
  • 슛이 X/B 로 끝나면 서버가 직전 레코드의 res 도 같은 값으로 덮어쓴다 (write-back, extra.lib.php:1211). applyResult() 가 이를 재현한다.

연결

DidInput 화면에 붙인 것

  • 위치 클릭 → 액트 → 결과가 레코드 하나로 쌓임
  • X/B 는 새 레코드가 아니라 직전 레코드의 결과로 반영
  • 연결이 끊기는 순간에만 Select 버튼 등장 — 진행 중에는 뜨지 않는다
  • 선수선택 UI 가 액트 입력창 자리에서 전환 (포메이션 유니폼 + Cancel / Submit)
  • BAP 실시간 카운트
  • 전/후반 전환, 분석 모드에서만 타이머 일시정지 가능

실시간 입력 전용 처리

레거시 배치는 마지막 미완료 루트를 강제로 마감하지만, 실시간 입력에서 그렇게 하면 아직 진행 중인 레코드에까지 DAP 가 붙어 선수 입력 버튼이 미리 떠버린다. 그래서 computeAttackPaths(records, { closeTrailing: false }) 로 호출한다.

운영 기준으로 맞춘 것

X / B 로 끝난 레코드는 Select 를 띄우지 않는다. 레거시 코드의 표시 조건은 is_tap == 1 && act 있음 뿐이라 X/B 를 직접 막지는 않는다(DPlayInputFragment.java:1661). 다만 서버 판정에서 X/B 가 루트를 끊지 않아 그런 공격은 대부분 UPP(무효)로 분류되어 is_tap = 0 이 되므로, 화면 결과는 같다.

확인 필요

현재 구현은 res 로 직접 막는 방식이라, 슛까지 이어진 공격 중간에 낀 X/B 레코드에서는 레거시와 결과가 갈릴 수 있다. 실데이터로 확인 필요.

모든 버튼은 항상 활성 상태. 블락·실책이 언제 나올지 알 수 없으므로 상황에 따라 흐려지지 않는다. 유효하지 않은 클릭은 각 핸들러에서 무시한다.
