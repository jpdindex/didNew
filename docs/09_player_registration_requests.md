# 선수 등록 요청

분석관이 외부 자료를 직접 확인하고 양식에 입력한다. 이 흐름에는 HTML 수집을 연결하지 않는다.

## 사용

- 데이터 관리 → 선수 등록 요청하기 (`/manage/player-requests`).
- 라인업 화면 좌측 하단 분석관 정보 아래의 버튼은 요청 화면으로 같은 탭에서 이동하고 경기의 리그·시즌·팀·날짜를 채운다.
- 분석관은 요청을 제출하고 본인 요청의 처리 상태를 조회한다.
- `jpdindex@gmail.com` 계정은 전체 요청을 확인하고 수정 저장 또는 승인할 수 있다. 수정 저장은 승인 대기를 유지하며, 승인을 누르면 DB에 등록한다.
- 승인은 기존 선수 확인을 거친다. 기존 선수 연결 시 기본 프로필은 유지한다. 다른 클럽 소속과 기간이 겹치면 자동 이적 처리하지 않고 검토하도록 중단한다.
- 명단 적용 시작일은 경기일 이하여야 한다. 가입일이 확인되면 그 날짜를 입력한다.

## 저장과 권한

- `playerRegistrationRequests`: 제출값, 수정·승인 반영값, 요청자·검토자·상태(승인 대기/등록 완료)·버전·최종 playerId.
- 승인 트랜잭션에서 `players`, 선수 하위 `contracts`, 현재 클럽의 `teams/.../squad`, 요청 승인 상태를 함께 저장한다.
- 동일 승인 재시도는 등록된 결과를 반환한다. 동일 영문 전체 이름·생년월일의 신규 선수 ID는 결정적으로 생성하여 동시 중복 등록을 막는다.
- 중복 확인은 생년월일·이름의 색인 조회를 사용한다. 전체 선수 DB나 외부 HTML을 스캔하지 않는다.
- `playerRegistrationRosterVersions`: 승인된 명단 변경을 표시한다. 다음 경기 재진입에서 명단 캐시를 갱신한다. 별도 새로고침 UI를 요구하지 않으며 저장된 라인업·RAW 기록은 수정하지 않는다.
- API는 로컬에서도 Firebase Bearer 토큰을 검증한다. UID 헤더나 Swagger 키로 승인 권한을 대신하지 않는다.
- 브라우저에서 요청 컬렉션에 직접 쓸 수 없다. 선수·팀 직접 쓰기는 관리자에게 제한한다.

운영 적용 시 프런트엔드, 백엔드, `firestore.rules`를 함께 배포해야 한다. 이 작업은 로컬 구현이며 자동 배포하지 않는다.

## Transfermarkt 자동화 이식 시 필수 조건

별도 `transfer_automation`의 기준 Excel/SQLite를 DIDNew의 기준 DB로 사용하지 않는다. 수집 결과를 아래 DID 필드와 식별자에 맞춰 변환한 뒤 변경 후보로 저장해야 한다.

| 외부 정보 | DID 기준 |
|---|---|
| 선수 ID | 기존 `playerId`를 유지하고 Transfermarkt ID는 별도 매핑 |
| 팀·리그·시즌 | `teamId`·`leagueId`·`seasonId`로 해석. 팀명 문자열만으로 연결 금지 |
| 국적·포지션·주발 | DID의 국가 코드, GK/DF/MF/FW, L/R/B 값 |
| 생년월일·소속 기간 | 기존 선수/계약의 날짜 표기와 기간 의미에 맞게 변환 |
| 신규 발견 | 기존 DB 선수인지 먼저 확인하고 신규 선수/소속 추가를 구분 |
| 이적·변경 | 출처·발생일·이전/이후 값·검토 및 반영 이력 보존 |
| 추적 대상 묶음 | `pl2`·`laliga2`를 실제 리그나 2부 등급으로 해석 금지 |

선수 등록 요청 양식을 수집기로 바꾸거나 분석관 제출 때 외부 페이지를 자동 요청하지 않는다. 수집기의 저장 계층과 엑셀 기준 대조 부분은 Firestore 기준으로 교체해야 한다. 엑셀은 DB 내역 다운로드 용도로 분리한다.
