# DID 재구축 현황

레거시 DID(PHP/Gnuboard5 + Android APK)를 마이그레이션하지 않고, **Nuxt 4 기반으로
처음부터 다시 만드는** 프로젝트의 현재 상태 정리.

최종 갱신: 2026-08-31

---

## 1. 한눈에

| 항목 | 내용 |
|---|---|
| 프론트 | Nuxt 4 (app 디렉터리), Vue 3 `<script setup>`, TypeScript |
| 인증·저장 | Firebase Auth (이메일/비밀번호) + Firestore — **신규 프로젝트 `JPD-DID`** |
| 백엔드 | Python API — 미착수 |
| 대상 기기 | 태블릿 웹앱 (네이티브 앱 불필요). 화면 기준 해상도 **1280 × 800** |
| 사용자 | 사내 직원 전용. 공개 가입 없음 |
| 완료된 화면 | 로그인 · 경기 선택 · 팀/라인업 선택 · DID-INPUT |
| 오늘 작업 | KPI 로직(공격루트·DAP·BAP) 포팅 + DidInput 연결 |

> `JPD-DID` 는 기존 `aifootballx` 와 분리된 별도 Firebase 프로젝트다.
> 나중에 Python API + Firebase Admin SDK 로 `aifootballx` 에 동기화할 예정이며,
> 이 작업은 가장 마지막으로 미뤄두었다.

## 3. 화면 흐름

```
로그인 → 경기 선택 → 팀/라인업 선택 → DID-INPUT
 /login   /schedule    /TeamSelection    /DidInput
                ↓
          데이터 관리 (/manage) — 준비 중
```

### `/login`
Firebase Auth 연동 완료. 짧은 ID 입력 시 `@jpd-did.internal` 로 변환해 이메일 형식을
맞춘다(`@` 가 포함되면 실제 이메일로 그대로 사용). **아이디 저장**은 localStorage,
**자동로그인**은 Firebase persistence 모드(`browserLocal` ↔ `browserSession`)로 구현.

### `/schedule`
날짜·경기 선택. 로그아웃, 데이터 관리 진입 버튼. 선택한 경기 정보(날짜·리그·라운드·
경기장·시간·홈/원정)를 쿼리로 다음 화면에 전달.

### `/TeamSelection`
- 팀 선택 (홈/원정) → 선택에 따라 선수 명단 교체
- 포메이션 4종 (4-4-2 / 4-3-3 / 3-5-2 / 4-2-3-1)
- 선발 11 + 후보 7 = **18슬롯**. 클릭 배치와 **드래그 앤 드롭** 모두 지원
- 진영 선택 (좌/우) — 구역코드 계산의 기준이 된다
- **입력 모드** — `분석`(기본, 일시정지 가능) / `실시간`(정지 불가, 이동만 가능)
- 기록/수정 시작 시간 위젯 (클릭 편집)
- `TEST` 버튼 — 포메이션·18슬롯·진영을 랜덤으로 채워 QA 시간 단축
- 18슬롯 + 포메이션 + 진영이 모두 채워져야 `전반전 시작` 활성화

### `/DidInput`
실시간 이벤트 입력 화면. 상세는 6~9장.

### `/manage`
팀 관리 / 선수 관리 / 경기 일정 관리 — **3개 모두 준비 중 (미착수)**.

> 새로고침하면 사라진다.

## 5. 좌표 · 구역 체계

`03.areacode.sql` 이 유일한 근거다. (APK 디컴파일로도 같은 개념을 확인했다.)

- 원본 캔버스 **971 × 634**
- 가로 6칸 × 세로 3칸 = **18구역**
- 열 경계 `[0, 152, 318, 484, 651, 818, 971]`
- 행 경계 `[0, 180, 451, 634]`
- 진영 선택값 + 전/후반으로 방향(`L`/`R`)이 정해지고, 방향에 따라 번호가 반전된다
  (`zone = dir === 'L' ? 19 - zoneR : zoneR`)
- **구역 1~6 = 상대 진영 앞 1/3 (공격영역)**, 10 이상 = 자기 진영

경기장을 클릭하면 해당 구역이 잠깐 밝아졌다 사라진다(420ms).

## 6. 용어 변경

레거시 명칭을 신규 명칭으로 전부 교체했다. 근거는 PPT
`DID 프로세스 슬라이드_20251120` 슬라이드 7 과 레거시 코드 주석.

| 레거시 | 신규 | DB 컬럼 | 근거 |
|---|---|---|---|
| TMP | **TAP** | `gr_is_tmp` | PPT 슬라이드 7 |
| TAP | **DAP** | `gr_is_tap` | PPT 슬라이드 7 + `extra.lib.php:4021` (`21.12.29 TAP->DAP 용어 변경`) |
| CTP | **DTP** | `gt_ctp` | PPT 슬라이드 7 |
| CSP | **DSP** | `gt_csp` | `extra.lib.php:2414` (`csp = dsp`) |
| CTS / CTA / CTM / CTB | **DTS / DTA / DTM / DTB** | `gr_is_ct*` | `CT*` → `DT*` 패턴 |

변경하지 않음 — `UPP` `UTP` `STP` `TTP` `GTB` `GTM` `SHOT` `ASR` `GSR` `SSR` `BAP`.
신규 명칭 근거를 찾지 못했고, 대부분 화면에 노출되지 않는 내부 분류값이다.

> ⚠️ **`TAP` 은 레거시와 신규에서 의미가 다르다.**
> 레거시 TAP = 신규 DAP, 신규 TAP = 레거시 TMP. 옛 쿼리·문서를 볼 때 반드시 확인할 것.

화면 노출 8개 KPI — `TAP` `DAP` `DTP` `SHOT` `ASR` `GSR` `SSR` `BAP`

## 7. KPI 로직 — `app/utils/didLogic.ts`

평점(rating) 계산은 범위에서 제외했다.

### 공격루트 분류

| 분류 | 조건 |
|---|---|
| **UPP** | 기본값. 슛도 없고 공격영역에도 못 들어간 단순 점유 |
| **UTP** | 공격영역(1~6) 진입. 레코드 2개 이상 필요<br>예외 — 1개여도 K/F 면 인정 (레거시 2021.12.13 추가) |
| **DTP** | 루트 안에 슛(S/H/R)이 포함됨 |
| **STP** | DTP 인데 레코드가 1개뿐인 단독슛 |
| **DSP** | DTP 중 유효슈팅을 포함하는 건 |
| **TTP** | UTP 또는 DTP (유효 공격 총합) |

**루트를 끊는 조건은 두 가지뿐이다.**
1. 결과가 나옴 (`res != 'O'`) — X, B, 슛 결과
2. 직전 레코드와 **4초 초과** 공백

### DAP 판정

- **DTP / STP** — 루트 안의 모든 레코드가 DAP 로 인정된다.
- **UTP** — 공격영역 진입 시점 이후는 전부 인정, 진입 **이전은 2개까지만** 인정.
- act 가 비어 있는 레코드는 항상 제외 (`isDap = !!act`).

### 선수 역할

DTP/STP 루트를 역순으로 훑으며 부여한다.
`DTS(슈터)` → `DTA(어시스터)` → `DTM(메이커)` → 그 이전 전원 `DTB(빌더)`.
골로 이어진 경우 `AST` `GTM` `GTB` 가 함께 붙는다.

### BAP

DAP 와 무관한 별도 카운터. `Ready` / `Keep` 상태머신으로 판정하며
4초 공백, 결과 발생, 공격영역 진입, 중앙선 돌파 등이 트리거다.

## 8. 핵심 발견 — 레거시에 계산이 두 벌 있고 서로 다르다

| | 단말 (APK)<br>`calcMadenPath` | 서버 배치<br>`extra.lib.php:2148` |
|---|---|---|
| lookahead 보정 | **없음** | **있음** |
| X/B 로 루트가 끊기나 | **끊긴다** | 안 끊긴다 |
| BAP 중앙선 분기 | `empty(act)` 검사 없음 | `empty(act)` 검사 있음 |

서버 쪽 주석은 *"DID와 동일한 기준 및 순서로 판단하기 위한 처리"* 라고 되어 있지만,
실제로는 단말과 결과가 달라진다.

**우리가 다시 만드는 것은 입력 단말(DID) 자체이고, 실제 운영에서 관측된 동작도
"X/B/슛이 나오면 연결이 끊긴다" 이므로 단말 로직을 기준으로 삼았다.**

## 9. 데이터 모델 — 플레이 하나 = 레코드 하나

APK 디컴파일로 확인한 실제 동작.

| 단계 | 동작 | 결과 |
|---|---|---|
| 액트 버튼 (C/P/K/F/S/H/R) | `setActCode(act)` + `setResCode("O")` | `act='C', res='O'` |
| 결과 버튼 (X/B) — 비-슛 | 액트 레코드의 `res` 를 채우고, **결과 레코드를 하나 더 남긴다** | `act='P', res='B'` → 뒤에 `act='', res='B'` |
| 결과 버튼 (X/B) — 슛 | `setActCode(null)` + 직전 레코드에 write-back | `act='', res='X'` |
| 골대 존 결과 | 해당 슛 레코드의 `res` 만 덮어씀 | `act='S', res='GOAL'` |

즉 `P` 를 누르고 `B` 를 누르면 표에 **두 줄**이 남는다 — `P | B` 가 먼저, 그 뒤에
`(빈칸) | B`. 뒤따르는 결과 레코드는 `act` 가 비어 있어 DAP 대상에서 자동 제외된다.

- `'O'` 는 계산용 임시값이 아니라 **앱이 실제로 저장하는 값**이다
  (`DPlayInputDefaultFragment.java:151`).
- 결과를 별도 레코드로 나눠 저장하지 않는다.
- 슛이 X/B 로 끝나면 서버가 **직전 레코드의 `res` 도 같은 값으로 덮어쓴다**
  (write-back, `extra.lib.php:1211`). `applyResult()` 가 이를 재현한다.

### 액트 / 결과 코드

| 구분 | 코드 |
|---|---|
| 액트 | `C` 크로스 · `P` 패스 · `K` 코너킥 · `F` 프리킥 · `S` 슛 · `H` 헤딩 · `R` 직접 프리킥 |
| 결과 | `O` 진행중 · `X` 실책 · `B` 블락 · `GOAL` · `L`/`H`/`R` 유효슛 · `LX`/`HX`/`RX` 빗나감 |

## 10. DidInput 연결

### 동작하는 것

- 위치 클릭 → 액트 → 결과 순서로 기록
- **X/B 는 직전 액트 레코드의 결과로 들어가고, 결과 레코드가 한 줄 더 생긴다**
- **연결이 끊기는 순간에만 `Select` 버튼 등장** — 진행 중에는 뜨지 않는다
- **선수선택 UI 가 액트 입력창 자리에서 전환** (포메이션 유니폼 + Cancel / Submit)
- BAP 실시간 카운트
- 전/후반 전환, `분석` 모드에서만 타이머 일시정지 가능
- 기록 표는 **시간 오름차순** — 가장 최근 기록이 맨 아래에 쌓이고, 표가 자동으로 따라간다
- `Result` 컬럼은 성공(진행중)이면 `O` 를 그대로 표시한다

### 실시간 입력 전용 처리

레거시 배치는 마지막 미완료 루트를 강제로 마감하지만, 실시간 입력에서 그렇게 하면
**아직 진행 중인 레코드에까지 DAP 가 붙어 선수 입력 버튼이 미리 떠버린다.**
그래서 `computeAttackPaths(records, { closeTrailing: false })` 로 호출한다.

### 운영 기준으로 맞춘 것

- **X / B 로 끝난 레코드는 `Select` 를 띄우지 않는다.** 뺏기거나 막힌 결과에는 우리
  팀에서 입력할 선수가 없다는 운영 기준이다.
  레거시 코드의 표시 조건은 `is_tap == 1 && act 있음` 뿐이라 X/B 를 직접 막지는
  않는다(`DPlayInputFragment.java:1661`). 다만 서버 판정에서 X/B 가 루트를 끊지 않아
  그런 공격은 대부분 UPP(무효)로 분류되어 `is_tap = 0` 이 되므로 화면 결과는 같다.
  **현재 구현은 `res` 로 직접 막는 방식이라, 슛까지 이어진 공격 중간에 낀 X/B
  레코드에서는 레거시와 결과가 갈릴 수 있다. 실데이터로 확인 필요.**
- **모든 버튼은 항상 활성 상태.** 블락·실책이 언제 나올지 알 수 없으므로 상황에 따라
  흐려지지 않는다. 유효하지 않은 클릭은 각 핸들러에서 무시한다.

## 11. 검증

타입체크 `strict` + `noUncheckedIndexedAccess` 통과.

| 시나리오 | 결과 |
|---|---|
| 단독슛 골 | STP, DSP, 슈터에 DTS |
| 골 빌드업 | DTP + 역할 DTB → DTM → DTA(+AST) → DTS |
| 진입 전 빌드업 4개 | 앞 2개 제외, 가까운 2개만 DAP |
| 4초 초과 공백 | 루트 2개로 분리 |
| 슛 → B | act 비워짐 + 직전 레코드 write-back |
| BAP 중앙선 돌파 | `CROSS ATTACK` 발생 |

브라우저에서 입력 → 연결 끊김 → Select → 선수선택 → Submit 전 과정 확인.
